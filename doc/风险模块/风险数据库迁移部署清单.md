# 风险数据库迁移部署清单

## 适用范围

本文说明风险预警模块第一阶段的 Flyway 数据库初始化与升级流程。风险分仅用于辅助决策，不代表暴跌概率，不构成投资建议，也不保证收益。

## 上线前准备

1. 使用 MySQL 8，并确认应用使用 JDK 21、Maven 3.9 及以上版本。
2. 对目标库进行可恢复的全量备份，并在隔离环境完成恢复演练。
3. 确认目标库当前结构与 `V1__baseline.sql` 一致；如有漂移，先处理差异，不要直接执行风险迁移。
4. Flyway 的 `baseline-on-migrate` 默认保持为 `false`，禁止依靠自动 baseline 猜测存量库状态。
5. 数据库地址、账号和密码通过部署平台或环境变量提供，文档与仓库中不得写入真实凭据。

## 空库部署

空库不执行 baseline，直接运行 `flyway migrate`。Flyway 将依次执行：

- `V1__baseline.sql`：建立当前股票规则系统基线表。
- `V2__risk_warning_foundation.sql`：增加风险表、公共索引及 `signal_direction` 回填。

迁移后运行 `flyway info`，确认版本 1 和版本 2 均为 `Success`，并检查 `flyway_schema_history`。

## 存量库部署

存量库已经具备 V1 表结构时，必须显式登记基线，再执行 V2：

```bash
flyway -baselineVersion=1 baseline
flyway migrate
flyway info
```

执行前应核对以下事项：

- `stock_signal_daily.signal` 中的历史 `high_risk` 原值会保留用于审计。
- `signal_direction` 会根据历史信号和多空分数回填；同分或无法判断时为 `watch`。
- 迁移不会把风险闸门切换为强制模式，`risk_gate_result.enforced` 固定为 `0`。

## 验收检查

1. 七张 `risk_*` 表均存在，唯一键和查询索引完整。
2. `stock_signal_daily.signal_direction` 无空值，历史 `signal` 未被覆盖。
3. 随机检查 `observed_at <= available_at`，不可用数据的数值字段保持 `NULL`。
4. 重复执行 `flyway migrate` 不产生新变更，版本校验无 checksum 异常。
5. 应用启动日志显示 Flyway 校验通过，风险评分与闸门仍未自动启用。

## 回滚与故障处理

Flyway Community 不自动执行 SQL 回滚。V2 执行失败时停止应用发布，不要手工修改 `flyway_schema_history`。先保留现场与迁移日志，根据备份恢复整个目标库，修复迁移脚本后在隔离环境重新验证。若 V2 已成功但应用验收失败，优先回滚应用版本并保留新增表；只有经过数据审计并获得明确变更批准后，才可按备份方案恢复数据库。
