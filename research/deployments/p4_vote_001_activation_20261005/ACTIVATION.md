# P4-VOTE-001 启用问题修复

最新状态：用户随后授权多方案修改，P4 已与原方案同时启用，8080已加载新服务。见[多方案部署记录](../multi_strategy_signals_20261005/DEPLOYMENT.md)。以下保留修复中间状态。

`2026-10-05`（北京时间）确认启用失败有两层原因：三个基本规则处于草稿且禁用，规则组必须先启用成员；应用方案必须先启用规则组。依赖满足后，旧研究闸门又将待最终验证与运行状态混为一谈，直接拒绝 P4 的辅助启用。前端共享请求层对 HTTP 400 抛出普通 `{code,msg}` 对象，页面只识别 `Error`，因此隐藏了实际原因。

修复后，规则组/方案接口将业务错误转换成 `Error` 并保留后端 `msg`。P4 的运行用途固定为 `usageMode=auxiliary`，研究状态固定为 `researchStatus=pending_final`；启用与最终验证分开，客户端提供的 `verified` 不被采信。三选二规则、阈值、股票范围、预测周期、上涨定义及最终验证窗口没有改变。

三个基本规则已通过原 API 启用，规则组为 `active/v2`。依赖写入和回读在 `dependency-enablement-api.json` 保存；原启用方案的快照未改变。

应用方案启用仍等待用户选择运行方式：当前 `rule_strategy` 的数据库唯一约束只允许一个启用方案，直接启用 P4 会停用原方案。并行运行需要分别保存各方案信号，不能仅删除切换逻辑。此前用户要求保留原方案，因此本次未擅自切换。

37项相关后端测试、12项前端接口错误回归测试、前端类型检查及后端构建通过。新构建临时运行于8081并回读确认 `auxiliary/pending_final`，见 `fixed-runtime-readback.json`；验证后临时服务已停止。现在8080服务由IDE启动，没有开发热重载；磁盘源码与构建已修复，运行中的旧进程尚未加载修复。待运行方式确定后再加载新构建、执行方案启用并回读。
